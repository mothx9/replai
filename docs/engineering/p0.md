This dossier owns PERFORMANCE.BASELINE methodology and evidence, not project

characterize the current implementation; they do not promise performance or

## Benchmark architecture

[The runner](../../tools/perf/run.py) prepares and measures in separate phases.
[Components](../../tools/perf/components.rs) compiles the exact private source
files by path in a separate Cargo workspace. It does not expose private internals
through REPLAI's API, copy a competing implementation, or change the production
dependency graph. [The PTY host](../../tools/perf/pty_host.rs) links the canonical
`replai` package and calls the actual public Linux `Interaction` façade.

| Boundary | Timed work | Excluded from that timer |
| --- | --- | --- |
| Decoder | Incremental bytes, recognized-key ownership, bounded rejection; completed stream | Input generation, expected stream construction |
| Compatibility keymap | Already-recognized key to normalized action | Key allocation/recognition; no configurable REPLAI keymap |
| Editor | One mutation/navigation/admission on a prepared editor | Preparing text, cursor and history; postcondition checks |
| Layout | `Frame::new` including construction and clipping | Editor setup and output encoding |
| Render | `transition` on ready frame, old visible frame retirement, mutations | Both layouts; explicit erase included in erase scenarios |
| VT encode | Mutation vector to encoded String | Mutation construction, terminal transport |
| Transport | Real Linux `Resource::write`, 1–4096 bytes into an empty PTY | Resource acquisition and verified readback/restoration |
| Complete engine interaction | Action/editor/layout/render/encode | System transport and OS wait strategy |
| Real Linux interaction | Input delivery to exact final VT byte on PTY master | Open/setup; submission verification follows timing |
| Output | Actual synchronous `external_output` call through terminal write return | Deadline pacing sleeps; no editing/output concurrency |

The terminal emitter hands one encoded batch to a transport call, including
empty batches. Logical mutations, encoded bytes, transport calls and kernel
write syscalls are separate quantities. Empty transport calls perform no kernel
write. `render/external_output` characterizes erase plus frame restoration;
`external_output/engine_transaction` and Linux output include the entire notice.
Layout/render output lifetime is retained at the allocation snapshot. The final
returned-value drop is excluded, while drops inside an operation are included.

## Workloads and contract bounds

Definitions live in the executable fixture, not an informal score:

- Drafts: 0, 8, 64, 1024, 4096, 16384, 65536, 262144 and 1048576 bytes.
  ASCII, Latin, CJK, combining, emoji, joined emoji, mixed code/JSON/prose and
  multiline units repeat; ASCII padding reaches exact byte sizes without
  splitting UTF-8/graphemes. Boundary positions derive from grapheme iteration.
- The public Editor requires explicit limits and has no implicit 64 KiB default
  or hard maximum. This fixture declares a bounded **1 MiB, 100-history-entry
  host profile**; examples use 64 KiB. This is an admitted caller configuration,
  not a newly expanded library limit. At exactly 1 MiB, growing edits reject;
  editor results label rejection, render insertion is unsupported. Separate
  0-byte, 64 KiB and 1 MiB paste rejection oracles preserve atomicity.
- Editor: beginning/middle/end insertion and deletion, backspace, left/right,
  Home/End, short/4096-byte completion replacement, clear, history admission,
  navigation and unsent-draft restoration. Movement from prepared positions is
  distinct from the Linux compound Home + 32 Rights + insert scenario. A separate one-key
  middle insertion prepares the cursor before timing.
- Protocol: printable classes, navigation aliases, Home/End/Delete, mixed valid
  bytes, invalid UTF-8, unknown escapes and 64–65536-byte malformed sequences.
  The malformed test explicitly asserts one bounded rejection and resumed text.
- Layout: widths 20/80/240, height 24, beginning/middle/end cursor, clipped
  viewports, wrapped prompts, multiline drafts, wide and joining graphemes.
  `visible_logical_rows` counts returned rows, not all intermediate rows.
  Literal multiline prompt fields are rejected by the existing contract; a
  560-byte wrapped prompt is the admitted multiline visual scenario.
- Paste: 1/4/16/64/256 KiB and 1 MiB; ASCII, UTF-8 prose, code, JSON and mixed
  multiline text. Framing/normalization, final-delimiter normalization, normalized
  keymap, insertion, layout/redraw and real PTY are measured separately. The
  decoder owns CRLF normalization; the keymap only transfers String ownership.
- History: 10/100/1000/10000/100000 retained entries of 64 bytes; admission/oldest
  eviction, up/down, restoration and retained growth. Preparation is excluded
  from navigation timers and included in the separate memory-growth operation.
- Output: 16/80/1024/4096/16384-byte multiline chunks at 5/20/50/100/200 calls/s
  over two seconds. Rate waits occur outside the timer. CPU is child rusage
  including startup/close, conservatively labelled; deadline misses are retained.
- Completion owns a fixed host-selected replacement only, not discovery.
  Decoder/keymap/request/replacement/render remain separately visible.

All mutating workloads assert exact text/cursor or exercise an existing
qualified transition. Render ASCII transitions additionally compare a VT100
screen/cursor against fresh geometry. Unicode layout retains F0's executable
cell/grapheme oracles; VT100 does not prove every terminal's ZWJ policy. Real
PTY runs compare exact produced bytes, exact submission and captured termios.

## Measurement method and distortion

Release profile: opt-level 3, debug information level 1, unwind, no LTO/native-CPU
change. Microbenchmarks use 3 groups × 21 samples, with 2 untimed warmups per
group. Setup/validation are outside timers. Keymap and constant-time operations
near `control/timer_black_box` are timer-floor observations, not trustworthy
nanosecond comparisons. No overhead is subtracted.

Linux interactions/comparisons use 31 observations after 2 warmups. The largest
paste runs remain bounded; their first byte through final visible bytes includes
bulk delivery/backpressure and the driver's one-byte processing. Python input
submission begins the timer; exact expected output length and byte equality end
it. A production-source predictor runs outside measurement and its resulting
text must agree with independently declared expected text. Resize times include
waiting for the current driver to notice dimensions, but not an arbitrary test
sleep. This endpoint includes process scheduling and PTY master delivery; it is
an upper bound on completed terminal writes, not emulator repaint or photons.

All valid samples are retained. Median, nearest-rank p95/p99, min/max and median
absolute deviation are serialized. Group medians expose run variability. With
31 samples p99 is the observed maximum, not a well-resolved tail estimate.
Output at 5 Hz supplies only 10 calls and has the same limitation. CI numbers
are never authoritative or compared across operating systems.

[Allocation instrumentation](../../tools/perf/allocation.rs) uses a separate
`allocations` build. It counts successful allocation/reallocation requests,
requested bytes, retained live-byte delta and peak logical live-byte delta
relative to the pre-operation baseline. A realloc contributes its requested
new size; allocator internals, metadata, arenas, fragmentation and transient
old/new realloc overlap are not observable. These are **not RSS or actual
physical peak memory**. The instrumented run supplies no timing numbers.
Stack footprints use `size_of`, heap retention uses allocator observations.
Memcheck remains a correctness oracle and is never timed as performance.

Idle calls/rusage are collected untraced, including a deliberate zero-timeout
busy-poll case. Separate `strace` invocations count dimensions, reads, polls and
actual terminal writes. Interactive syscall windows use syscall entry wall-clock
timestamps; a poll already pending before delivery can be excluded. Idle/output
counts after READY include synchronization and close, explicitly labelled.
Tracing is restricted to input bursts up to 4 KiB; substantial paste traces are
not needed for timing and are not extrapolated into asserted syscall totals.
Missing optional tracing tools produce `unavailable` records, never zeros.

## Harness integrity refinements

The first complete component run is retained at its exact measured source
identity. Review added directed Unicode movement because the repeated corpora
can end in ASCII padding: the original `editor/left` at end describes that tail,
not a guaranteed step across a joined emoji. `movement` explicitly steps across
non-ASCII graphemes near the middle/end, records their byte lengths and verifies
both cursor endpoints. A bounded single grapheme containing up to 524287
combining marks separates grapheme complexity from document length; chain layout
is measured too. `render_edge` crosses wrap/viewport boundaries to qualify the
append fast-path cutoff directly.

A preliminary Linux harness run exposed a sender error above the PTY input
queue: it waited for output instead of write readiness on backpressure, so the
library correctly expired incomplete paste. The sender now waits for writability
with the same selector and no sleep, uses a memoryview, and fails promptly on
child exit. A 64 KiB paste is included in CI smoke; full 1 MiB cases must pass
exact output/submission/restoration checks. No decoder timeout was changed.
Windows metadata capture classifies unavailable load-average observation as
null, with an absence test. Comparison traffic is drained through process exit;
its count includes post-submission teardown, while timing still ends at the
submission receipt. These are harness corrections, not library optimizations.

## Component findings

### Protocol and normalized action boundary

At 64 KiB the ASCII decoder takes 514 microseconds (about 127 MB/s decimal);
Latin UTF-8 706, CJK 653, combining 729, emoji 592 and ZWJ 641 microseconds.
Invalid UTF-8 takes 157 microseconds at the same byte count. Logical-input
counts differ: byte throughput is not equal to decoded-key throughput.
Navigation, Home/End/Delete aliases, unknown escapes and bounded malformed
streams have separate IDs/counters. Each malformed stream asserts bounded
rejection and progress; none grows an unbounded pending sequence. Printable
key ownership allocates separately from the compatibility keymap. Keymap
ownership transfers and the completion-request event are mostly below the
observed timer floor and require no measured heap allocation; they cannot be
ranked by their serialized zero/sub-microsecond medians.

The convenience field `input_bytes_per_second` is the input-size/median quotient.
Use it as throughput for completed decoder/paste streams. For single editor or
render operations its numerator describes the prepared draft, not bytes actually
copied/decoded; it is not a transport throughput claim.

### Editor scaling (question 1)

Representative ASCII operation medians below are **microseconds**, rounded to
one decimal; `<1` is deliberately not a nanosecond claim. Each admitted operation
has an exact postcondition. At 1 MiB the three growing insertions are rejected
and marked R: those values are rejection latency, not successful edit latency.

| Operation | 64 B | 4 KiB | 64 KiB | 256 KiB | 1 MiB |
| --- | --- | --- | --- | --- | --- |
| append | <1 | 31.4 | 481.9 | 1928.5 | <1 R |
| insert_begin | <1 | <1 | 1.9 | 4.2 | <1 R |
| insert_middle | <1 | 44.0 | 717.1 | 2924.7 | 8011.3 R |
| backspace_end | <1 | 29.2 | 476.2 | 1897.0 | 7916.0 |
| backspace_middle | <1 | 14.5 | 236.1 | 962.8 | 3919.6 |
| delete_end | <1 | 29.6 | 474.6 | 1904.4 | 8034.8 |
| delete_middle | <1 | 14.5 | 240.6 | 962.8 | 4077.4 |
| left | <1 | <1 | <1 | <1 | <1 |
| right | <1 | <1 | <1 | <1 | <1 |
| home | <1 | <1 | <1 | <1 | <1 |
| end | <1 | <1 | <1 | <1 | <1 |
| completion_short | <1 | 28.8 | 498.3 | 1906.1 | 7876.6 |
| completion_large | <1 | 44.6 | 534.2 | 1930.8 | 7952.6 |

`delete_end` intentionally means Delete with the cursor already at end: text
stays unchanged, yet boundary handling costs about 8 ms at 1 MiB. Backspace is
the actual deletion of the last grapheme. Completion replaces the middle-to-end
range; the substantial candidate is `min(4096, available suffix length)` bytes.
History-up includes saving/copying the current unsent draft; restoration moves
back the saved draft. Clear's retained capacity is not freed by that operation.

Append, middle insertion, backspace/delete and completion show approximately
linear growth over the larger admitted sizes. Beginning insertion is far
cheaper but its copy cost also grows with size. Home/End, ordinary one-grapheme
movement, clear, navigation to a fixed short history item and moving back the
saved draft show no comparable whole-draft linear traversal in these samples;
sub-microsecond values are too quantized for a precise exponent. History admission
and saving a growing draft scale with text length. These are observed finite
ranges, not complexity proofs or fitted universal laws.

The text class matters: at 64 KiB, ZWJ append/middle insertion/backspace medians
are 257/391/257 microseconds versus ASCII 482/717/476; ZWJ backspace at 1 MiB is
4.19 ms versus ASCII 7.92 ms. Equal byte counts contain different grapheme counts
and widths. This does not mean Unicode is intrinsically cheaper. All eight
classes and empty/tiny/1/4/16/64/256 KiB/1 MiB drafts are executable; the summary
retains all operations for ASCII/ZWJ scaling and the other classes at
64 B/64 KiB/1 MiB. The largest successful editor medians in the full matrix
are mixed-text completion (9.11 ms) and mixed/multiline backspace (9.10 ms) at
1 MiB, rather than the ASCII values alone.

### Actual grapheme movement (question 2)

Directed movement verifies non-ASCII boundaries rather than timing ASCII padding
at the end of a repeated corpus. Ordinary CJK, combining, emoji and 11/25-byte
ZWJ steps stay below one microsecond in median even in 1 MiB drafts; for example,
a 25-byte ZWJ left step is about 0.4 microseconds. Differences at this scale are
near clock/setup/scheduling effects and do not establish a whole-draft scan.

A single long grapheme is a different workload:

| Combining-chain draft | Left (us) | Right (us) | Layout (us) | Visible rows |
| --- | --- | --- | --- | --- |
| 64 B | 0.1 | 0.2 | 0.7 | 1 |
| 4096 B | 7.2 | 11.0 | 31.3 | 1 |
| 65536 B | 108.8 | 179.8 | 502.0 | 1 |
| 1048576 B | 1579.2 | 2895.6 | 8023.4 | 1 |


At the largest size there are 524,287 combining marks in a 1,048,575-byte
grapheme plus one padding character. Step latency scales with this individual
grapheme's complexity. It is bounded by the declared draft limit but can consume
milliseconds. P1 needs both ordinary-document and adversarial-grapheme evidence.

### Layout and render (questions 3–5)

ASCII end-cursor layout at 80 columns grows from 1.59 ms at 64 KiB to 6.35 ms at
256 KiB and **27.14 ms at 1 MiB**, although each returns only 23 visible rows.
At 1 MiB, widths 20/80/240 take 30.42/27.14/26.50 ms. ZWJ layout at 1 MiB/80
columns takes 11.20 ms. Construction before clipping, grapheme count and text
class dominate; a clipped viewport is not a bound on layout work. The full
matrix's largest layout median is 33.15 ms for 1 MiB multiline text with the
cursor at beginning, 80 columns (middle/end are about 33.14/33.09 ms). Beginning,
middle and end cursors, multiline drafts and wrapped prompts remain separate
records. Width policy is unchanged: F0's grapheme widths are an implementation
policy, not proof that every emulator renders combining/ZWJ/wide cells identically.

Ready-frame transitions for a 64 KiB ASCII draft (layout and VT encoding excluded):

| Scenario | Median (us) | Mutations | Clear-line ops | VT bytes |
| --- | --- | --- | --- | --- |
| append | 0.5 | 1 | 0 | 1 |
| cursor_left | 8.5 | 141 | 23 | 2041 |
| middle_insert | 5.8 | 141 | 23 | 2103 |
| middle_delete | 5.9 | 141 | 23 | 2103 |
| history_replace | 0.8 | 75 | 23 | 233 |
| resize | 1.9 | 140 | 23 | 717 |
| multiline_change | 4.7 | 140 | 23 | 2004 |
| full_redraw | 8.5 | 142 | 24 | 2042 |
| external_output | 8.2 | 142 | 24 | 2042 |


The append case produces one suffix mutation/one byte at about 0.5 microseconds,
versus 8.5 microseconds and 2,042 bytes for explicit erase/redraw of the prepared
frame. This roughly 17-fold **ready-frame transition** difference does not avoid
layout reconstruction, and is not an interaction speedup. Encoding that full
redraw takes about 0.6 microseconds separately. One logical output batch is not
142 writes: actual interaction traces normally show one kernel write for a
nonempty batch. Empty batches perform no write. VT byte counts are not syscalls. The largest ready-frame median in the
full matrix is 19.0 microseconds for 256 KiB ZWJ resize to 20 columns; the
complete operation still requires the separately measured layout.

The append path requires compatible visible geometry and an extending final
line with the cursor following its suffix. Direct width-80 edge tests observe
one byte for 75-to-76-byte text, 88 bytes on the following wrap, and 2,018 bytes /
139 mutations at the 1,836-byte viewport-wrap boundary. Cursor movement is not a
cursor-only renderer optimization today: it erases/redraws visible content.
A full Ctrl-L in the short real-PTY case produces 20 bytes in one write; the
64 KiB ready-frame full redraw above describes a different viewport workload.

The complete 64-byte append engine/editor/layout/render/encode path takes
2.25 microseconds. Isolated terminal `Resource::write` medians are approximately
2.5–2.8 microseconds for 1–4096 bytes into an empty PTY, with exact readback and
mode restoration. The real two-process 64-byte append is about 49 microseconds.
These independently prepared timers are not an additive profiling breakdown;
they establish that simple-key wall latency includes substantial scheduler/IPC/
PTY costs, while large-draft engine work is dominated by editor/layout. No exact
percentage of end-to-end time is assigned to a layer by subtraction.

## Variance, limitations and decisions

All per-operation distributions, min/max, MAD and microbenchmark group medians
remain in the committed summaries. For example, 64 KiB ASCII append has median
482 microseconds and p95 511; 1 MiB ASCII layout has median 27.14 ms and p95
27.86 ms. The short PTY append ranges from 19.8 to 79.1 microseconds with MAD
9.7, while the final 4096-byte REPLAI burst has median 278.59 ms, p95 285.67 ms
and maximum 354.09 ms. Small repeated runs can move noticeably even on the same
recorded VM. No outliers were trimmed and no hosted-runner regression threshold
was introduced. The directed-movement allocation supplement uses five samples
in one group, explicitly recorded; timing still uses 63 samples in three groups.

The clock control frequently measures zero, with a roughly 0.042-microsecond
nonzero step. Serialization in microseconds preserves raw resolution but does
not justify nanosecond accuracy. For short operations use the timer-floor
classification; for PTY/tails use realistic rounded figures and sample counts.
Large pasted text and long ordinary typed bursts are different workloads.
Cold start, physical display latency, remote SSH transport, slow terminal
backpressure, multi-hour output, concurrent writers and cross-OS system backends
are not established here. Allocator live-byte deltas are not physical peak RSS.
Literal multiline prompts remain contractually unsupported; wrapped prompts
are measured. Consumer sizes are absolute, with no matched empty-consumer delta.

Measured findings motivate the following future investigations, without choosing
or implementing an optimization:

| Question | Evidence and deferred engineering implication |
| --- | --- |
| 13 — P1 candidates | Linear append/middle/delete/completion boundary work; even Delete at end takes 8 ms at 1 MiB. Separate string movement from boundary validation; preserve bounded rejection. Ordinary movement is cheap, but one huge combining grapheme takes 1.58/2.90 ms. Consider storage/index strategies only against these distinct workloads and their memory costs. |
| 14 — P2 candidates | A 23-row viewport still constructs a 27-ms / 104,892-allocation 1 MiB layout. Investigate layout reconstruction/clipping and temporary ownership as well as frame transitions. Cursor changes and wrap boundaries erase/redraw; bytes, mutation counts and latency need separate targets. A normal nonempty transaction already reaches one kernel write here, so batching must start from that fact. |
| 15 — P3 candidates | Roughly 10 idle dimension checks/s at long timeouts, about 102-ms median resize observation, busy zero-timeout polling, and per-byte read/poll/dimension-query traffic during paste. Investigate readiness/resize driving and bounded work per host turn without assuming an executor or a thread model. |
| 16 — F1 implications | A host-driven API must make blocking behavior and work bounds explicit: a bulk paste is atomic but about one second at 1 MiB on this driver; a ready-frame append does not imply cheap full interaction; a synchronous output call can be short while still consuming redraw/transport bandwidth. Simple and driven tiers should share correctness/measurement seams. No new public API is designed or frozen here. |

Architecture supplies separable engine/layout/render/protocol/transport seams.
Implementation supplies current String/history/grapheme traversal, frame
construction and redraw policy. The workload supplies draft/grapheme length,
viewport and output rate. Linux/PTY transport and scheduling supply additional
syscall/backpressure/wakeup costs. The evidence distinguishes these boundaries;
it does not infer perfect additive causality from unrelated medians.
